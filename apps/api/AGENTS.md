# Pousse API — Rules for agents

`apps/api` is the REST API of the Pousse monorepo: Fastify 5 + TypeScript,
consumed only by `apps/mobile`. It is still a **scaffold** — no business
route exists yet. This document puts into practice the decisions
already accepted in `../../docs/adr/` (0001 to 0007, and 0012 for the
language); when in doubt, the ADR wins and this file gets fixed to stay
consistent with it, never the other way around.

## 0. Language (ADR-0012)

**Everything in `apps/api` is in English**: identifiers, file and folder
names, module names and route prefixes, table and column names, enum and
stored code values, error messages (thrown or returned), log messages,
comments and doc comments. The API never returns French text: errors carry
an English `message` and a stable `code` (e.g. BetterAuth's
`INVALID_EMAIL_OR_PASSWORD`), and the mobile client maps the code to its
French UI copy. Don't add a translation layer to the API.

ADRs 0001–0011 are written in French and use French names; ADR-0012 maps
them to the code names (`prenom` → `first_name`, `nom_famille` →
`last_name`, `defis` → `challenges`, `souvenirs` → `memories`, `lettres` →
`letters`). Use the English names when writing code.

## 1. Framework and validation (ADR-0001)

- Fastify 5, `fastify-type-provider-zod` to validate inputs and **serialize
  outputs**. Every route declares a Zod response schema: a field missing from
  the schema must never reach the client, not even through a developer
  mistake — that's the guarantee schema serialization gives and no manual
  test can replace.
- `@fastify/swagger` generates the OpenAPI spec from the same schemas. Never
  maintain API docs separately from the code.
- Pino is already embedded (`Fastify({ logger: true })`): don't add a second
  logger.

## 2. Data (ADR-0002, ADR-0005)

- **Drizzle is the single source of truth for the physical schema.** The
  database is never changed outside migrations generated by `drizzle-kit`
  from `src/shared/db/schema.ts`. No hand-written SQL outside generated
  migrations.
- Every constraint the database can express (composite uniqueness,
  `check()`, partial index, composite key, cascade) is declared in the
  Drizzle schema, never in a trigger. See ADR-0005's split table for the
  exact list of declarative rules vs. those that stay in the service layer
  (child's age, twenty-four-hour window, weekly draw…).
- The relational API is `defineRelations` (RQB v2); don't use the old
  callback style from `drizzle-orm/_relations`.
- In a partial index, the `.where()` predicate is written with the `sql`
  template, never with `eq()`.

## 3. Authentication (ADR-0003)

- BetterAuth in its default configuration: no JWT plugin, no refresh token.
  A session is revoked immediately; never reintroduce a stateless token to
  "simplify" a call.
- The BetterAuth `user` table stands in for the logical model's `PARENT`.
  `child.parent_id` references `user.id`, not a separate `PARENT` table.
- Mounting on Fastify: disable body parsing on the auth route, copy
  **every** `Set-Cookie` header (not just the first one), mount the route as
  a wildcard.
- The mobile app must read the session cookie from `expo-secure-store` and
  add it explicitly to business requests — the Expo plugin only attaches it
  automatically to the auth client's calls.

## 4. Modular split (ADR-0006)

Required structure, each module carrying its own layers:

```
src/
  modules/
    auth/       journal/       challenges/       memories/       letters/
  shared/
    db/         errors/        config/
```

- **A route never touches a repository directly** — always through a
  service.
- **A service may call another module's service. It never touches another
  module's repository.** That's the rule behind the fix applied on the
  mobile side (`InitializeChildProgress`, see `apps/mobile/AGENTS.md`):
  apply the same reflex here before writing a service that imports another
  module's repository.
- `shared/` only holds infrastructure (database connection, error types,
  configuration) — no business logic.
- A module is exposed as a Fastify plugin (`app.register(xModule, {
prefix: '/x' })`, see `src/app.ts`). Crossing a module boundary must fail
  at startup, not only in review.
- Emotions and badges don't naturally belong to any module: they're attached
  to the module that mainly consumes them (badges → `challenges`) rather than
  creating a catch-all technical module.

## 5. Tests (ADR-0007)

- Jest as the test runner. `fastify.inject()` for route tests — never
  Supertest, never a real HTTP server started in tests.
- Testcontainers provides a real PostgreSQL instance to integration tests.
  **No mocking of the data access layer**: a database constraint
  (uniqueness, `check()`, cascade) is only verified against a real
  PostgreSQL.
- Isolation between tests through a rolled-back transaction, not by
  recreating the schema; the container starts once for the whole suite.
- Levels: unit (pure service logic, no database), integration (routes +
  repositories + constraints, PostgreSQL container), end-to-end (main
  journeys from the mobile app, dedicated environment).

## 6. Conventions

- Kebab-case file names, one service/repository/route per file.
- Internal imports through Node's native `#/*` mapping (`package.json` →
  `imports`), **with the `.js` extension** and `/index.js` for a module:
  `import { buildApp } from '#/app.js'`. In development, the `development`
  condition resolves to `src/` (tsx); in production, to `dist/`
  (`node dist/server.js`). Don't reintroduce tsconfig `paths` aliases: `tsc`
  doesn't rewrite them and the compiled code would no longer start.
- `import type` for type-only imports.
- `npx tsc --noEmit` must pass before a change is considered done.
- No new dependency without a strong reason — in particular, don't add an
  abstraction layer on top of Drizzle or Fastify that the ADRs didn't pick
  (Prisma, Kysely, NestJS, Express: see the alternatives already rejected in
  the matching ADRs before suggesting them again).
